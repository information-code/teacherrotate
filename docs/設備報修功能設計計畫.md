# 設備報修功能設計計畫

> 撰寫日期：2026-08-24（草案，待課務／資訊組確認開放問題後定稿）

## 一、目標與定位

讓老師遇到設備問題（例：電視沒有網路）時，能在 30 秒內完成報修；報修後立刻獲得「自助排解」引導，有機會不必等人到場就解決；管理端則以案件狀態機追蹤每一件報修，並靠**標準化的問題字典**把大量報修聚合成可決策的統計（常見問題、解決情況、未來資金投入方向）。

與既有「設備借用」系統的關係：**共用設計模式（權限、照片上傳、單例 config），但資料獨立**。報修對象（教室電視、網路、冷氣、廣播…）多半是固定裝置，不在借用清單裡，所以不直接綁 `equipment` 表（見開放問題 Q1）。

## 二、核心機制：問題聚合（本功能的靈魂）

老師報修時的描述五花八門（「電視沒網路」「螢幕連不上 wifi」「YouTube 打不開」其實是同一件事）。如果統計時用原始文字分組，數據就是一盤散沙。設計兩層機制（2026-08-24 決策：**不做前端即時建議／同義詞比對**，聚合統一靠管理端歸類）：

1. **標準問題字典（repair_issues）**
   管理端在「報修設定」為每個設備項目維護常見問題清單（例：電視 → 沒有網路／沒有畫面／沒有聲音／遙控器失靈）。老師報修時**優先點選**這些選項——點選即天然聚合。字典涵蓋不了的，老師自由繕打送出。

2. **事後歸類（管理端）**
   自由文字送出的案件，在案件報表中標示「未歸類」，管理者可一鍵：
   - **歸入既有標準問題**（該案件統計歸戶）
   - **升級為新的標準問題**（代表這是字典沒料到的新病灶，之後老師可直接點選）

   統計頁一律以 `issue_id` 聚合；未歸類案件單獨列出並提醒管理者處理，確保數據長期乾淨。

## 三、使用者流程

### 教師端：設備報修（/teacher/repair）

**Step 1 填報**
- 選設備項目（下拉／大按鈕）→ 顯示該項目的常見問題 chips → 點選，或選「其他」自由輸入
- 地點（教室／場地，文字或從教室清單選）
- 照片上傳（選填，多張，沿用 service-role 上傳＋簽名網址讀取模式）
- 送出 → 寫入 `created_at` 時間戳，畫面明確顯示「已於 HH:mm 送出」

**Step 2 自助排解頁（送出後自動進入，之後也可從案件詳情回來）**
- 顯示所報「標準問題」對應的教學內容：影片（YouTube 嵌入）或步驟說明；自助內容只掛在問題層（設備項目層不設通用指南——2026-08-24 決策），自由繕打或問題未設內容時顯示聯絡資訊為主
- 常駐顯示：**距離報修已經過 X 小時 Y 分**
- 顯示可呼叫的維護人員（老師／學生志工）姓名＋聯絡方式（電話分機／LINE）
- 「✔ 問題已解決」按鈕 → 選擇「自行排除」或「問題自行消失」→ 案件轉為已解決並保留紀錄，管理端不需出勤
- 案件狀態列（與管理端同步）：已送出 → 已接案 → 已出勤排查 → 已報廠商 → 結案

**Step 3 我的案件列表**
- 列出自己歷來報修：時間、設備、問題、目前狀態、經過時間；未結案件置頂

### 管理端

**1. 報修設定（/admin/repair-config）**
- **設備項目**：名稱、啟用、排序（一個名稱就是一類，比照借用系統不做類型層）
- **問題字典**：掛在設備項目下；名稱、啟用、排序
- **自助內容**：每個問題可掛影片網址＋步驟文字；只掛問題層，項目層不設
- **維護人員**：姓名、身分（老師／學生）、聯絡方式、備註、排序
- **SLA 門檻**：未處理超過 N 小時黃色警告、M 小時紅色警告（存單例 config JSONB，比照 equipment_config）

**2. 案件報表（/admin/repair-cases）**
- 待辦導向列表：報修時間、**經過時間（依 SLA 上色警告）**、報修人、設備、地點、問題（未歸類者標示＋歸類按鈕）、照片、解決註記（自行解決／問題消失／尚未解決）
- **狀態機**（單向推進，附時間戳）：
  `待處理 → 已接案 → 已出勤排查 → 已報廠商協助 → 結案`
  - 「已報廠商」可跳過（自行修好直接結案）
  - 老師按「已解決」→ 自動轉入「已解決（自行排除／問題消失）」輕量結案，仍留在報表與統計中
  - 每次狀態變更同步顯示於教師端案件詳情
- 結案時可填處理紀錄（做了什麼、花費），供統計使用
- 篩選：狀態／設備項目／日期區間／是否逾 SLA

**3. 報修統計（/admin/repair-stats）**
- 問題排行（以標準問題聚合，這就是第二節機制的產出）
- 設備項目排行、地點排行（哪間教室最常壞）
- 月趨勢（報修量、結案量）
- 解決方式占比：自行解決率／到場排查／報廠商——自行解決率高代表自助內容有效
- 平均處理時長（各狀態間隔，來自時間戳）
- 「報廠商比例高＋重複發生」的項目 → 標示為**建議投入資金汰換**的候選清單

## 四、資料模型（migration 040_repair.sql）

```
repair_items       設備項目字典：id, name, active, sort_order, fallback_guide JSONB
repair_issues      標準問題：id, item_id FK, name, aliases TEXT[], guide JSONB
                   (video_url, steps_md, photos), active, sort_order
repair_contacts    維護人員：id, name, role('teacher'|'student'), contact, note,
                   active, sort_order
repair_config      單例 config（id=1 CHECK）：SLA 門檻等 JSONB
repair_reports     案件：id, teacher_id FK profiles(ON UPDATE CASCADE，虛擬帳號地雷),
                   item_id FK, issue_id FK NULL, custom_issue TEXT NULL,
                   location TEXT, photos JSONB(path[]),
                   status('pending'|'accepted'|'dispatched'|'vendor'|'closed'),
                   resolved_kind(NULL|'self'|'vanished'|'fixed'),
                   created_at, accepted_at, dispatched_at, vendor_at, closed_at,
                   admin_note TEXT
```

- 照片沿用 `equipment-photos` bucket、路徑前綴 `repair/`（省一次 bucket 建置；若要權限分離再開新 bucket）
- `issue_id` 與 `custom_issue` 二擇一必填（CHECK）；歸類動作＝把 `issue_id` 補上（`custom_issue` 保留原文）
- 狀態時長統計直接用五個時間戳欄位，MVP 不另建 events 表

## 五、權限與導覽

- `lib/staff.ts` PERM_GROUPS「設備管理」群組加三個 key：
  `repair-config`（報修設定）、`repair-cases`（案件報表）、`repair-stats`（報修統計）
- 三個管理頁比照現制：`guardPage([key])` ＋ API `hasPerms()`
- 教師端側欄加「設備報修」，全教師可用

## 七、開放問題（請確認）

1. **報修設備來源**：獨立字典（本計畫預設）？還是要能選到借用系統的資產編號（例如報修某台特定筆電）？可折衷：字典為主，選填「資產編號」文字欄。
2. **自行解決是否即結案**：本計畫預設「自動輕量結案、保留紀錄」；或要管理者確認後才結？
3. **通知**：老師送出報修時要不要主動通知管理者？現系統無推播，選項是（a）管理頁 badge＋儀表板待辦（Phase 4）、（b）比照借用逾期的「複製通知貼 LINE」反向操作、（c）不通知靠定期巡報表。
4. **學生維護人員聯絡方式**放進系統給全校老師看，隱私上是否 OK？或只顯示姓名＋「請透過導師聯繫」？
5. **報修人範圍**：只有教師？行政（無教職）帳號要不要能報修？
